## Scope and implementation

The actual saved-draft review previously trusted its RPC acknowledgement. A real save followed by a lost response left the owner seeing a raw fetch error even though revision 1 and its audit row had committed. The new recovery path independently checks the signed-in owner, original source and exact target revision before and after submission. It never presents an acknowledgement payload as saved evidence.

`src/lib/ownerReview.ts` clones/freezes the original source, expected revision and exact title/condition changes. It uses actual Auth getUser, explicit owner/source filters, complete counted catalogue context and a counted target-revision audit query. Before a deliberate write the source must remain the same unapproved DRAFT/revision with no catalogue children. The existing RPC retains its optimistic expected-revision lock and atomic report/audit write; its migration bytes and signature are unchanged.

A confirmed result requires matching audit identity, owner, source, target revision and exact changes, plus matching current report revision, merged review facts and transaction timestamps. Earlier sibling fields and review metadata must remain preserved. The original model report, photo manifest, initial AI and user context are compared separately; owner review never becomes AI fact or a comparable.

`SavedDraft` holds an uncertain request in memory. **Check review save** performs GET/read operations only. **Retry same review save** checks actual state first and submits at most one deliberate RPC with the held original expected revision and changes when still eligible. A committed matching revision resolves without another write. Missing/denied/incomplete/different evidence stays uncertain. A competing review or later saved revision cannot be overwritten by recovery; the owner is told to copy the retained text before reloading.

Review text stays selectable/copyable with read-only fields while facts are held. Selection, grouping, photo-correction, catalogue approval, correction saving and paid research actions cannot conflict with the pending save. A ref guards rapid repeated actions before React renders. Same-owner reauthentication retains pending facts. Changing account/report remounts the private view and ignores late results. Completion/uncertainty receives keyboard focus. Existing theme/design tokens are retained; no CSS, dependency or brand change.

## Remaining gates and limits

- Exact current Instructions/authoritative version and source review remain prerequisites for source publication/activation. Hosted S3/CDN/TLS acceptance needs a suitable separate non-production target; loopback acceptance cannot certify hosted infrastructure.
- Pending changes remain in memory. Refresh can reload committed owner-review facts; an unsent request cannot be recovered after the page closes. No durable operation journal or orphan reconciliation is added.
- The existing RPC serialises review revisions, but original-source comparison is client preflight/readback, not a new transaction-level source CAS. A change occurring between reads may produce a retained conflict/uncertainty requiring reload. Current owner direct database mutation/INSERT rights remain; this is not WORM or proof of a unique request event. Identical same-owner changes at the same target revision fulfil the held facts without claiming independent request identity.
- Target-revision evidence is completely counted (at most one row), not a complete browser of all prior revisions. Existing context bounds remain 100 original objects/catalogue children and 500 photos/links/corrections; excessive/incomplete data fails closed. Research history remains scoped latest 100.
